## 1. Conventions

- All primary keys are `UUID` (v4), generated by the application layer or `gen_random_uuid()`.
- All monetary columns are `numeric(10,2)` or `numeric(12,2)` for aggregate/ledger values — **never** `float`/`double`.
- All timestamps are `timestamptz`, stored in UTC.
- Table names: `snake_case`, plural. Column names: `snake_case`.
- Every table has `created_at`; mutable tables also have `updated_at` maintained by a trigger or the ORM.
- Enums are implemented as native Postgres `enum` types where the value set is stable, or `varchar` + check constraint where it may need frequent extension (documented per table).

## 20. Important Constraints (Summary)

- Foreign keys enforced at the database level (not just application level).
- UUID identifiers everywhere; no auto-increment integer PKs exposed externally.
- Monetary values use `numeric`, never `float`/`double`.
- `(subscription_id, scheduled_date)` uniqueness on `meal_occurrences` prevents duplicate generation — this is a correctness invariant, not a performance optimization.
- Soft deletion (`status = ARCHIVED`/`DEACTIVATED`) is used for user-facing catalog entities (`menus`, `menu_items`, `users`); financial and audit tables (`payments`, `ledger_entries`, `audit_logs`) are never deleted, soft or hard.
- `ledger_entries` are immutable and application-role write-restricted to `INSERT` only.

## 21. Indexes

| Table | Index | Purpose |
|---|---|---|
| subscriptions | `(customer_id)` | Customer's subscription list |
| subscriptions | `(provider_id)` | Provider's subscriber list |
| subscriptions | `(status)` | Job queries (e.g., active subscriptions needing generation) |
| meal_occurrences | `(subscription_id)` | Subscription calendar view |
| meal_occurrences | `(scheduled_date)` | Provider daily preparation dashboard |
| meal_occurrences | `(status)` | Operational queues |
| meal_occurrences | `(provider_id via subscription join)` — denormalize `provider_id` onto `meal_occurrences` | Avoids join for the hottest query (today's prep list by provider) |
| payments | `(subscription_id)` | Billing history |
| payments | `(idempotency_key)` unique | Duplicate-charge prevention |
| notifications | `(user_id, read_at)` | Unread notification badge |
| ledger_entries | `(wallet_id, created_at)` | Provider statement generation |
| device_tokens | `(user_id)` | Push fan-out |
| audit_logs | `(entity_type, entity_id)` | Entity history lookup |

> **Note on denormalization:** adding `provider_id` directly to `meal_occurrences` (in addition to reaching it via `subscription_id`) is a deliberate read-optimization for the single most frequent query in the system — a provider's "today's meals" list — and should be kept in sync via the same transaction that writes the row, not a background job.

## 22. Migration Strategy

- Drizzle Kit manages schema migrations; every migration SQL file is checked into version control and is forward-only in production (no destructive rollback migrations against live data).
- Schema changes that affect `meal_occurrences` or `payments` require a backward-compatible two-step rollout (add nullable column → backfill → enforce not-null in a later migration) to avoid write-path downtime.
- Seed data for local/staging environments lives in `backend/src/db/seed.ts` and must never be run against production.
